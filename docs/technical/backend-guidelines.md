# Backend Guidelines

Rules for `apps/server` (Fastify + TypeScript) and the shared packages. They exist so the codebase stays easy to navigate as it grows. Rules are numbered so code reviews can cite them ("breaks B4"). Rules marked 🔒 are enforced in CI (ESLint or dependency-cruiser). The others are checked in review.

## Shape: a modular monolith

One process, split into **modules by business capability**. Each module owns its tables, its use cases and its HTTP routes, and exposes a small public API to other modules. Inside a module, code is split into three layers.

```
            ┌────────────── module "decks" ───────────────┐
 HTTP ────► │ decks.routes.ts    (Fastify adapter, thin)  │
 jobs ────► │ decks.jobs.ts      (pg-boss adapter, thin)  │
 WS   ────► │        │                                    │
            │        ▼                                    │
            │ decks.service.ts   (use cases, rules, tx)   │ ──► other modules' index.ts
            │        │                                    │
            │        ▼                                    │
            │ decks.repository.ts (Drizzle queries)       │ ──► Postgres
            └─────────────────────────────────────────────┘
```

## Server layout

```
apps/server/src/
  main.ts                 Entrypoint: load config, buildApp, listen, graceful shutdown. Nothing else
  migrate.ts              Entrypoint: apply migrations (locally and as a one-off step before each deploy)
  app.ts                  Composition root: builds infra, services, registers plugins and modules
  config.ts               zod-validated environment, parsed once at boot
  db/
    client.ts             pg Pool + Drizzle instance, Db / Tx / DbExecutor types
    migrate.ts            runMigrations(): used by the entrypoint and by the test setup
    schema/<module>.ts    Drizzle tables, one file per owning module
    migrations/           Generated by drizzle-kit, committed
  plugins/                Global Fastify plugins (wrapped in fastify-plugin)
    error-handler.ts      AppError / zod error → HTTP response
    actor.ts              Resolves session or guest cookie → request.actor
    rate-limit.ts
    sse.ts                Server-Sent Events helper
  infra/                  Adapters to external systems that more than one module uses
    event-bus.ts          EventBus interface + in-memory implementation
    queue.ts              pg-boss setup
    mailer.ts
  modules/
    system/               Health/readiness. The reference example of the module pattern: copy its shape
    auth/  users/  credits/  decks/  generation/  billing/  rooms/  realtime/  moderation/
  lib/                    Small helpers with no domain knowledge: errors.ts (AppError), logger.ts (Logger type)
  test-support/           Test config and the global setup that migrates the test database
scripts/build.mjs         esbuild bundle: workspace packages bundled in, npm dependencies external
```

Services receive a `Logger` (from `lib/logger.ts`), not Fastify's logger type, so they never import Fastify (B4).

### Modules

| Module | Owns | May depend on |
|---|---|---|
| `users` | profiles, avatars, roles, bans | — |
| `auth` | Better Auth wiring, guest sessions, join tokens (JWT) | `users` |
| `credits` | `credit_ledger`, balance, reserve/commit/refund | `users` |
| `decks` | decks, cards, votes, search, card stats | `users` |
| `generation` | `generation_jobs`, prompt building, OpenRouter client, validation pipeline, the job runner (in-process now, pg-boss later) | `decks`, `credits` |
| `billing` | purchases, checkout, payment webhooks | `credits` |
| `rooms` | live rooms: `RoomRuntime` per room (the shell around game-core), creation/join over HTTP, room codes, lobby list, match history | `decks`, `auth` |
| `realtime` | WebSocket transport only: upgrade auth, decoding and validation, rate limits, heartbeat, the connection registry | `rooms`, `auth` |
| `moderation` | reports, auto-hide, admin endpoints | `decks`, `users` |

The dependency graph must stay acyclic. If two modules seem to need each other, one of them is doing the other's job: move the code, or publish an event on the `EventBus`.

Example: rooms must send messages to sockets, but `rooms` may not import `realtime`. So `rooms` defines a `RoomTransport` interface, `realtime`'s connection registry implements it, and `app.ts` passes it in (dependency inversion).

### Files inside a module

| File | Role | Allowed to import |
|---|---|---|
| `<m>.routes.ts` | Fastify plugin: route schemas, auth hooks, one service call per handler | own service, `protocol`, `plugins/*` types |
| `<m>.jobs.ts` | pg-boss handlers, as thin as routes | own service |
| `<m>.service.ts` | Use cases. Business rules, authorization, transactions, calls to other modules | own repository, other modules' `index.ts`, `infra`, `lib`, `game-core`, `protocol` |
| `<m>.repository.ts` | All SQL for the module's tables | `db/*` |
| `<m>.schemas.ts` | zod schemas used only by this module (shared ones go in `protocol`) | `zod` |
| `<m>.errors.ts` | Module-specific `AppError` factories (optional) | `lib/errors` |
| `index.ts` | **The module's public API**: service factory, its type, routes plugin | own files |
| `*.test.ts` | Tests, next to the file under test | anything |

When a service grows past ~300 lines, split it by use case into `services/<use-case>.ts` and keep `index.ts` as the only entry point.

## Rules

### Structure and dependencies

- **B1 🔒** Modules import other modules **only through their `index.ts`**. Never `../decks/decks.repository`.
- **B2 🔒** No import cycles between modules or files.
- **B3 🔒** Layers point downward only: routes/jobs → service → repository → db. Routes and jobs never touch `db/`. Repositories never import services.
- **B4 🔒** Services do not import `fastify`. A service must work the same when called from HTTP, a WebSocket message, a job, a script or a test.
- **B5** A repository queries **its own module's tables**. Read-only joins into another module's tables are allowed, for example deck search showing the creator's name. Writes to another module's tables always go through that module's service.
- **B6 🔒** `packages/game-core` has no I/O: no `fetch`, no DB, no `node:*` imports, no `Date.now()`, no `Math.random()`. Time and randomness are passed in.
- **B7 🔒** `packages/protocol` holds only zod schemas, types and constants (message types, error codes). No logic.
- **B8** An adapter used by one module lives in that module (e.g. `generation/llm/`). It moves to `infra/` only when a second module needs it.
- **B9** Add an interface only where a second implementation is planned: `EventBus`, `RoomRegistry` and `RateLimiter` (in-memory now, Redis when scaling out) and `LlmClient` (fake in tests). Nowhere else.

### Dependency injection (no container)

- **B10** Services are created by **factory functions with explicit dependencies**, and their type is inferred:

  ```ts
  // modules/decks/decks.service.ts
  export function createDecksService(deps: { db: Db; log: Logger }) {
    return {
      async search(query: DeckSearchQuery) {
        return decksRepository.search(deps.db, query);
      },
      // ...
    };
  }
  export type DecksService = ReturnType<typeof createDecksService>;
  ```

- **B11** All wiring happens in **`app.ts` (the composition root)** and nowhere else. It creates infra, then services in dependency order, then registers each module's routes with the services it needs as plugin options:

  ```ts
  // app.ts (sketch)
  const db = createDb(config.DATABASE_URL);
  const users = createUsersService({ db, log });
  const credits = createCreditsService({ db, log });
  const decks = createDecksService({ db, log });
  const generation = createGenerationService({ db, log, decks, credits, llm, queue, bus });

  await app.register(decksRoutes, { prefix: '/api/decks', decks });
  await app.register(generationRoutes, { prefix: '/api/decks', jobs: generationJobs });
  ```

- **B12** Don't decorate the Fastify instance with services (`app.decks`). Pass them explicitly as plugin options so each module's dependencies stay visible. Decorators are only for request-scoped context (`request.actor`).

### Services and business logic

- **B13** Authorization is checked **in the service**, not only in routes, because realtime and jobs call services too. Services that need it take an `actor` argument: `{ kind: 'user'; userId } | { kind: 'guest'; guestId } | { kind: 'system' }`.
- **B14** The service owns the transaction. It opens `db.transaction(async (tx) => …)` and passes `tx` to repository functions, which accept `DbExecutor = Db | Tx` as their first argument.
- **B15** **Never call an external API (OpenRouter, Stripe, email) inside a DB transaction.** Reserve the credit (transaction), call the model (no transaction), then save the deck and commit the credit (transaction).
- **B16** Anything that handles money or credits is **idempotent**. The ledger's `unique(reason, ref_id)` is the guard. Jobs and webhooks may run twice.
- **B17** Errors are thrown as `AppError(code, status, message)` (from `lib/errors`). `code` comes from the shared `ErrorCode` union in `protocol`, so the frontend can map it to a message. Don't throw strings or plain `Error` for expected failures.

### Database

- **B18** Schema changes go through `drizzle-kit generate`. Generated SQL is reviewed and committed. **Migrations are never edited after merge.** They are forward-only: fix a bad one with a new migration.
- **B19** Primary keys are `uuid` defaulting to `uuidv7()` (Postgres 18, time-ordered). Timestamps are `timestamptz`. Enum-like columns are `text` with a `check` constraint, matched by a TS string-literal union.
- **B20** No string-built SQL. Use the Drizzle query builder or the `sql` tagged template, which parameterizes values.
- **B21** Every query pattern that runs on a hot path or in a list endpoint has an index. Add it in the same PR as the query.

### Configuration, logging, security

- **B22 🔒** Only `config.ts` reads `process.env`. It parses with zod and **crashes at boot** if anything is missing. Everything else receives `config` through dependencies.
- **B23 🔒** No `console.*`. Use `request.log` in handlers and the injected `log` elsewhere. Create child loggers with context (`log.child({ roomCode })`, `{ jobId }`).
- **B24** Logs never contain secrets, cookies, tokens, emails or full prompts. pino `redact` is configured for `req.headers.cookie`, `req.headers.authorization` and `*.token`.
- **B25** Every input from outside the process is validated with zod at the edge: HTTP bodies/params/queries (route schemas), WebSocket messages (protocol schemas), env (config), webhook payloads, and **LLM output**.

### TypeScript style

- **B26 🔒** `strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`. No `any` (use `unknown` and narrow). No non-null `!` outside tests.
- **B27 🔒** Named exports only. No TS `enum`s (use `as const` objects or string unions). No barrel files except each module's `index.ts` and each package's entry.
- **B28** Files are `kebab-case.ts`. Module files are `<module>.<role>.ts`. Types and Zod schemas are `PascalCase` (`DeckSearchQuery`), and the inferred type has the same name as its schema.
- **B29** Prefer plain functions and object literals. Use a class only for long-lived stateful things (`RoomRuntime`).

## Fastify practices

| # | Practice | Why |
|---|---|---|
| F1 | Set `validatorCompiler`/`serializerCompiler` from `fastify-type-provider-zod` once in `app.ts`. Write route plugins as `FastifyPluginAsyncZod` | Request types are inferred from the schemas. No casts |
| F2 | **Every route declares `schema`**: `params`, `querystring`, `body` as needed, and `response` for each success status | Validation at the edge. Response schemas make serialization fast and **strip fields that shouldn't leak** |
| F3 | Handlers are `async` and **return** the payload. Never mix `return` with `reply.send()`. Set status with `reply.code()` | Avoids double-send bugs |
| F4 | Handlers contain no `try/catch` for expected errors. Thrown `AppError`s reach the single `setErrorHandler` in `plugins/error-handler.ts`, which returns `{ error: { code, message } }`. Unknown errors become a 500 with a generic message and are logged with the stack | One error format everywhere |
| F5 | Use encapsulation: module routes are **not** wrapped in `fastify-plugin` and are registered with a `prefix`. Only global infra plugins (`error-handler`, `actor`, `rate-limit`, `sse`) use `fastify-plugin` | Hooks and parsers stay scoped to their module |
| F6 | Request context uses `app.decorateRequest('actor', null)` plus an `onRequest` hook that sets it. Augment `FastifyRequest` once, in `plugins/actor.ts` | Correct Fastify 5 pattern for reference values |
| F7 | Authentication guards are `preHandler` hooks (`requireUser`, `requireVerifiedUser`, `requireRole('moderator')`) attached per route or per module plugin | Declarative, and visible at the route |
| F8 | The Stripe/MoR webhook needs the **raw body** for signature checks. Register a scoped `addContentTypeParser` (buffer) **inside the billing plugin only** | Encapsulation keeps the raw parser away from other routes |
| F9 | Set a global `bodyLimit` of 64 KB. Raise it per route only if needed | Small, predictable payloads |
| F10 | `trustProxy` trusts Caddy only. Caddy is configured with Cloudflare's IP ranges as trusted proxies, so `request.ip` is the real client IP | Rate limits by IP actually work |
| F11 | `@fastify/rate-limit` with the in-memory store, through the `RateLimiter` interface (B9) so it can move to Redis | |
| F12 | Mutating endpoints accept only `application/json` and check the `Origin` header against the site origin. Cookies are `HttpOnly; Secure; SameSite=Lax` | CSRF protection without tokens, given same-origin deployment |
| F13 | SSE goes through the `sse.ts` helper: `reply.hijack()`, write events to `reply.raw`, send a heartbeat comment every 15s, and unsubscribe from the `EventBus` on `close` | Avoids leaking listeners |
| F14 | Don't block the event loop: no sync crypto, no `*Sync` fs calls in request paths, no unbounded loops over user data. Deck validation and guess matching are fine (small inputs) | One process serves every room |
| F15 | No Express middleware (`@fastify/express`/`middie`). Use hooks and plugins | |
| F16 | Health endpoints: `GET /api/health` (process alive) and `GET /api/ready` (DB reachable). Both are excluded from request logging | |

## Realtime rules

The game is the one place where performance and correctness both matter a lot. It uses the **functional core, imperative shell** pattern.

```
 ws message ─► gateway: decode + zod-validate + rate-limit ─► RoomRuntime.handle(event)
 timer fire ────────────────────────────────────────────────► RoomRuntime.handle(event)
                                                                     │
                                       game-core: step(state, event, ctx) → effects[]
                                                                     │
                       RoomRuntime executes effects: send / schedule / cancel / loadDeck / disconnect / matchEnded / close
```

- **R1** `game-core` exposes `step(state, event, ctx): Effect[]`. `ctx` carries `now` and `rng`. `step` may mutate the `state` it's given, because each room exclusively owns its state and copying stroke lists 30×/s would be wasteful. It returns effects instead of doing I/O.
- **R2** **Who sees what is decided in `game-core`**, as `send` effects addressed to specific players. The secret-word and redacted-guess rules ([realtime-protocol.md](realtime-protocol.md#guess-feed-who-gets-what)) are therefore unit-tested without sockets.
- **R3** `RoomRuntime.handle` is **synchronous**. It never `await`s between reading and writing state, so events can't interleave. Async effects (`loadDeck`, `matchEnded`) run after the state update and report back as new events (`deckLoaded`) or are fire-and-forget with errors logged. If an effect triggers another event synchronously, the runtime queues it until the current one finishes.
- **R4** Every inbound message is parsed with the `protocol` discriminated union on `t`. If parsing fails, send `error` and increment a strike counter. After 10 strikes in a minute, close the socket with code 1008.
- **R5** `ws` runs with `maxPayload: 16 KiB`. Each connection has a token-bucket limit, plus the per-type limits (guesses 3/s, points per turn capped).
- **R6** A broadcast payload is serialized **once** and the same string is sent to each recipient.
- **R7** Backpressure: if a socket's `bufferedAmount` exceeds 1 MB, close it. The client reconnects and gets a fresh `room:snapshot`.
- **R8** Heartbeat: ping every 20s. Two missed pongs mark the player disconnected (grace period per [user-flows.md](../product/user-flows.md)).
- **R9** A `RoomRuntime` owns all of its timers and clears them in `dispose()`. The state machine emits `close` when a room is empty, idle or abandoned, and the runtime disposes itself. No timer is ever created outside a runtime.
- **R10** The WebSocket upgrade is authenticated with the `joinToken` in a `preValidation` hook on the `/ws` route. An invalid token is rejected before the socket opens.

## Lifecycle and graceful shutdown

`main.ts` uses `close-with-grace` (10s budget). On `SIGTERM`:

1. Stop accepting new rooms and new WebSocket connections.
2. Send `server:restarting` to every room, then close sockets with code 1012 (service restart).
3. Stop pg-boss gracefully. Active generation jobs either finish or are retried after restart. Credit handling is idempotent (B16), so a retry is safe.
4. `app.close()` runs every `onClose` hook, which closes the DB pool last.

## Testing

| Level | What | How |
|---|---|---|
| `game-core` | State machine, scoring, guess matching, card pool | Plain Vitest. **Simulated matches**: script events with a fixed `now`/`rng` and assert on effects. This is the largest test suite |
| Services | Use cases including transactions and the credit ledger | Against a **real Postgres** (the compose DB, a separate `test` database). Tables are truncated between test files. **Never mock the database** |
| Routes | Status codes, schemas, auth guards, error format | `buildApp(testConfig)` + `app.inject()`. No open port |
| Realtime | Join, a full turn, reconnect snapshot, per-recipient visibility | `app.listen({ port: 0 })`, real `ws` clients, Vitest fake timers through the injected clock |
| LLM | Generation pipeline | A fake `LlmClient` returning fixture decks (valid, invalid, refusal-like). **CI never calls OpenRouter.** Real-model checks belong to the eval script ([ai-deck-pipeline.md](ai-deck-pipeline.md#evaluation)) |

Tests live next to the code (`decks.service.test.ts`). Any bug fixed in `game-core` or guess matching gets a regression test first.

## Checklist for a new endpoint

1. zod schemas for input and output (in `protocol` if the web app uses them, otherwise `<m>.schemas.ts`).
2. Repository function(s), plus an index if needed (B21).
3. Service method with an authorization check (B13) and transaction (B14) if it writes.
4. Route with full `schema` (F2) and auth `preHandler` (F7), with one service call.
5. Tests: service (real DB) and route (`inject`).
6. If it's a new module: add it to the module table above and to the dependency-cruiser config.
